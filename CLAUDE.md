# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server (default port 5173)
- `npm run build` — production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run lint` — run Oxlint (config in `.oxlintrc.json`; react + oxc plugins, `react/rules-of-hooks` is an error)

There is no test runner configured in this project. `npm run lint` reports one known warning (`react(refs)` on `handlersRef.current = …` in `hooks/useMidiInput.js`); it is the intentional latest-callback-ref pattern, so leave it.

Two longer-form guides exist alongside this file and should be kept in step with it when behavior changes: [`docs/USER_GUIDE.md`](docs/USER_GUIDE.md) (how the app works, for end users) and [`docs/DEVELOPER_GUIDE.md`](docs/DEVELOPER_GUIDE.md) (the same architecture notes as this file, in prose form, plus a source map and a "making common changes" section).

**Verifying changes.** Behavior is checked with throwaway Playwright scripts (kept outside the repo) run against `npm run dev` at `localhost:5173`, not a committed suite. Handy facts for writing them: piano keys are buttons with `aria-label="C4"` (sharp-spelled ids); state persists in `localStorage` under `pianograph:progression`, `:title`, `:beatsPerMeasure`, and `:preferences` (`accidentals`, `midiAutoAdd`), so tests can seed a song with `addInitScript`; Web MIDI is exercised by replacing `navigator.requestMIDIAccess` with a fake input whose `onmidimessage` you call; the Share path is exercised by stubbing `navigator.share`/`canShare`. Real iPad Safari (share sheet, html-to-image rendering) cannot be tested here.

**Deploying.** It is a fully client-side static site: `npm run build` → upload `dist/`. Anything in `public/` is copied verbatim — the bundled piano samples (`public/samples/salamander/`) and Netlify's `public/_headers`. Vite's `base` is the default `/`; hosting under a subpath (e.g. GitHub Pages project sites) needs `base` set, and `audio.js` already builds sample URLs from `import.meta.env.BASE_URL`. There is no backend, so saved songs live only in each browser (hence Save as file / Open file — labeled that way in the UI, though the code and file format are still "export/import JSON"). `netlify.toml` pins the build command and publish directory so Netlify's "Import from Git" needs no manual config; the deployed site is public, watches the `main` branch, and redeploys automatically on push.

## Architecture

Pianograph is a React + Vite app for building piano chords/progressions. The core design decision that shapes everything else: **notes are represented as scientific-pitch-notation strings** (e.g. `"C4"`, `"C#4"`) everywhere — piano key ids, the MIDI hook's output, and both third-party libraries (Tone.js and Tonal.js) consume/produce this exact format natively, so there is no conversion layer between them.

### Key generation and octave range

`src/constants.js` defines `START_OCTAVE`/`OCTAVE_COUNT` (currently C2–B5, four octaves, to fit two-handed voicings with bass notes), the single source of truth for which octave range the interactive `Piano` renders. The piano scrolls horizontally (`.piano-scroll`, min 32px per key) instead of shrinking keys on narrow screens, and MIDI notes outside the rendered range are ignored in `Piano.jsx` (`validIds`) rather than becoming invisible phantom notes. `src/utils/pianoKeys.js` (`generateKeys`) builds the white/black key layout from that range and is shared by both the interactive `Piano` component and every read-only mini keyboard diagram — so the main keyboard and every diagram always agree on layout without duplicating the black-key positioning math. The mini-diagram rendering itself lives in one place, `src/components/PianoDiagram/PianoDiagram.jsx`, and is reused by both `ChordCard` and `LeadSheet` — don't reintroduce a second inline copy of that rendering loop. Unlike the main keyboard, each diagram *fits to its own notes*: it shows only the octaves the chord uses (minimum two) and shrinks its key width so it never exceeds 150px (`utils/diagramSize.js`, which `LeadSheet` also uses to size rows), so wide two-handed voicings get a wider, denser diagram instead of overflowing measures.

### Selection state lives in `Piano`, driven by three input sources

`Piano.jsx` owns the `activeNotes` Set (the single source of truth for "currently selected notes") and exposes it upward via an `onNotesChange` callback. Three independent inputs mutate this same state:
- Mouse clicks toggle a key (`toggleNote`) — click-to-select/deselect, sticky.
- MIDI note-on (via `hooks/useMidiInput.js`) selects a key and **latches**: note-off only stops the sound (`midiNoteOff`), it does not deselect. Latching is what frees both hands — the chord no longer has to be held while it is added. Keys physically down are tracked separately in `heldMidiNotes`. Three ways to commit a MIDI chord: the **auto-add** checkbox (persisted as `midiAutoAdd` in preferences, default on, shown only when a device is connected) fires `onMidiCommit` 350ms after the *last* held key is released (the delay lets two hands lift a moment apart, or a re-press, count as one chord; note-on and Clear keyboard cancel it); a **sustain pedal** press (CC 64, parsed by the hook as `onSustain`) commits immediately; or the ordinary Add chord button. `App.commitMidiChord` adds the chord and then calls `clearKeyboard()` (bumps `clearSignal` *and* empties the chord-search box/error, so a leftover search string doesn't sit next to an empty keyboard — the same function the Clear keyboard button uses) so the next chord starts fresh, unlike the Add chord button, which leaves the selection alone. Mouse clicks never auto-add.
- **Chord search** (`utils/chordSearch.js`, `searchChord(query)`) turns typed text into notes. `normalizeChordQuery` runs first, since Tonal's `Chord.get` accepts plain chord-symbol notation (already tolerant of case and whitespace, and slash-bass chords work natively) but not natural phrasing — it maps out spelled-out quality words ("Major" → "maj", "diminished" → "dim", ...), drops a trailing "chord", strips English ordinal suffixes ("7th" → "7"), strips parentheses/commas around altered extensions ("Ab9(#11)" → "Ab9#11", "C7(b9,#11)" → "C7b9#11" — Tonal rejects the punctuation but accepts the alterations run together), and special-cases both "half diminished" (any spacing/hyphenation, plus a redundant trailing "7"/"7th" — matched *before* the plain "diminished" rule or that rule would corrupt it first) and "dominant" (dropped before a number, since the number alone already implies dominant — "dom9" isn't recognized but "9" is; mapped to "dom" when it stands alone). `Chord.get`'s result is then voiced as a single ascending stack starting near the middle of the keyboard (each note placed in the lowest octave above the previous one). `App` applies the result to `Piano` via `applyPayload` (`{ notes, mode }`) + `applySignal`, generalizing the `clearSignal` render-time-diff pattern below to also support **merge** (add to the current selection, for a hand-clicked bass note plus a searched upper structure) alongside the default **replace**. Mode is bundled into `applyPayload` rather than read live off the `chordSearchMerge` checkbox, because editing a saved chord (below) is a second producer of `applySignal` that always needs `'replace'`, independent of that checkbox. Once applied, the notes are ordinary selected notes with no memory of having come from a search — adjusting them is just clicking keys, same as any other chord.
- **Editing a saved chord** reuses that same mechanism a third way: a chord card's name/diagram is a button (`onEdit`), not a sixth icon in the five-icon actions row (`@media (pointer: coarse)` already tunes those five to fit one card's width). Clicking it (`App.startEditChord`) pushes that entry's notes onto the keyboard (`mode: 'replace'`), sets `editingChordId`, and scrolls the compose panel into view, since the card is often below the keyboard. While `editingChordId` is set, `commitChord` — shared by the Add chord/Save changes button and the MIDI hands-free path — calls `updateChord(editingChordId, { notes, label })` instead of `addChord()`; because `updateChord` merges its patch, `beats` and any repeat marks on the entry are left alone. Anything that can strand `editingChordId` pointing at a gone or replaced entry (`removeChord` on that id, `clearProgression`, `applyImportedSong`) clears it too.

Gotcha already hit once: the `onNotesChange` callback must be invoked from a `useEffect` keyed on `activeNotes`, not from inside the `setActiveNotes` updater function — calling a parent's `setState` from inside another component's state updater triggers a React "Cannot update a component while rendering a different component" warning.

`useMidiInput` keeps latest `onNoteOn`/`onNoteOff` callbacks in a ref rather than the effect's dependency array, so it doesn't tear down and resubscribe to MIDI inputs on every render.

### Chord detection

`src/utils/chordDetection.js` wraps Tonal's `Chord.detect`. Two non-obvious details: notes are sorted low-to-high by pitch first (Tonal treats the *first* note as the bass, so click order would otherwise change slash-chord names), and `assumePerfectFifth: true` is passed so voicings that omit the 5th (common in jazz) still match. Note ids are always sharp-spelled (`D#4`), so both functions take an `accidentals` argument (`'sharps' | 'flats'`) and respell the ids (`Note.fromMidi` vs `fromMidiSharps`) before detecting — Tonal names roots from the spelling it's given, so this is what turns `D#maj7` into `Ebmaj7`. The preference lives in `App.jsx` state, persists via `loadPreferences`/`savePreferences` (`localStorage` key `pianograph:preferences`), and changing it re-runs `chordLabel` over every saved chord entry, because entries store their `label` string rather than recomputing it. Anything else that persists a derived label must be relabeled the same way. `chordLabel(noteIds)` is the single formatting function used both for the live chord-name header and for the label stored on each saved progression entry — same fallback rules apply everywhere (empty selection / single note / unrecognized cluster / detected chord name(s)).

### Audio playback

`src/utils/audio.js` plays through one of two module-level instruments behind `getInstrument()`: a `Tone.Sampler` of real piano recordings (Salamander Grand Piano, CC BY 3.0 — credited in the app footer), or the original `Tone.PolySynth` as a fallback. The samples are 17 clips (C, D#, F#, A across C2–C6, ~1.25 MB) bundled in `public/samples/salamander/` (with the license note) and served from the app's own origin, so it has no third-party dependency; `public/_headers` gives them a long Netlify cache lifetime. The Sampler pitch-shifts the notes in between. `App.jsx` calls `loadPiano()` on mount to start the download, and `getInstrument()` returns the synth until the sampler reports loaded — and forever if it fails (offline), so sound always works. `stopNote` releases on both instruments because a held MIDI note may have started on the synth just before the piano finished loading. Every audio path shares it:
- `previewNote` — short blip on mouse-click key activation.
- `startNote`/`stopNote` — sustain-while-held, used by MIDI note-on/off.
- `playChord` — one-off preview for a saved chord card's play button.
- `playProgression(chords, bpm, { onStepChange, onComplete })` — schedules every chord against `Tone.Transport` (`Tone.Transport.schedule((time) => instrument.triggerAttackRelease(...), offset)`, offset = running total of the preceding chords' `beats * beatSeconds`), so two 2-beat chords fill one 4/4 measure. Deliberately *not* raw `Tone.now() + offset` timestamps (an earlier approach) — Transport has its own pausable clock, which is what makes pause/resume possible at all, since a wall-clock offset can't account for time spent paused. `onStepChange` and `onComplete` are both scheduled the same way, via `Tone.Draw.schedule` so the React state update lands on the right visual frame rather than firing straight from the audio-scheduling callback; `onComplete` replaces an earlier `setTimeout(totalMs)` on the caller's side, which would've fired at the wrong wall-clock moment after any pause. `Tone.Transport.cancel()` runs at the start of every call to clear anything left scheduled from a run that was stopped rather than finished.
- `pauseProgression`/`resumeProgression` — thin wrappers over `Tone.Transport.pause()`/`.start()`.
- `stopProgression` — `Transport.stop()` (also rewinds position to 0) + `Transport.cancel()`, then `releaseAll()` on both instruments, since pausing alone only stops *new* notes from firing and doesn't cut off a chord already mid-release. `App.jsx`'s `playbackStatus` (`'stopped' | 'playing' | 'paused'`) drives which of Play/Pause+Stop/Resume+Stop shows in the toolbar, and gates the single-chord preview buttons the same way the old `isPlaying` boolean did.

`App.jsx`'s `runPlayback(chords)` is the one function that flips `playbackStatus` and calls `playProgression` — Play progression, a section's own ▶ (`progression.slice(index)`), and Play form (`buildPlayOrder(progression, formOrder)`, see below) are all just different arrays handed to the same function.

### Progression data model: two entry types in one flat array

The progression is a single flat array holding two kinds of entries, distinguished by `type`:

- Chord: `{ id, type: 'chord', label, notes, beats }` — `beats` is the entry's length in beats (default 4). The time signature is song-level state in `App.jsx` (`beatsPerMeasure`, N/4 for N in `TIME_SIGNATURE_OPTIONS`; persisted under `pianograph:beatsPerMeasure` and included in exports/imports). A chord's `beats` drives both its playback length and its width on the lead sheet, and a measure is *not* a chord — several short chords can share one measure. New chords default to one full measure, and `changeBeatsPerMeasure` converts chords whose `beats` equalled the old measure length to the new one (other lengths are left alone). The cards' one-click length chips come from `utils/beats.js` (`beatPresets`: 1, 2, one measure, two measures — expressed in beats because half of a 3/4 measure isn't a whole number).
- Section marker: `{ id, type: 'section', name }` — a structural marker (e.g. "A"/"B"/"Bridge") for song-form breaks, common in jazz standards. It carries no musical content.

Chords also carry optional **repeat marks** as flags on the chord itself (not as separate marker entries): `repeatStart` (a `|:` before the chord), `repeatEnd` (a `:|` after it), and `ending` (1 or 2). Unlike sections, these attach to a specific chord and are toggled from a chip row on its card, which avoids the reorder pain a separate marker entry would have; they travel with the chord when it moves, and `duplicateChord` drops the copy's repeat barlines (but keeps its `ending`). `cleanMarks` in `utils/repeats.js` is the one place that filters/validates these fields, used by `normalizeEntry`, the import parser, the exporter, and the layout code. `unfoldRepeats` (same file) turns the array into **play order** for `playProgression`: a repeat block starts at the latest `repeatStart` chord, section marker, or previous repeat end; each repeat end jumps back once; on the second pass `ending: 1` chords are skipped so ending 2 plays next. Only endings 1 and 2, no nesting, no repeat counts, no D.S./D.C./Coda.

`endsRepeat(progression, index)` (also in `repeats.js`, exported) is what actually decides a repeat end — `entry.repeatEnd === true`, *or* it's the last chord of a run of `ending: 1` (i.e. the next entry isn't also `ending: 1`). That second clause is deliberate: a first ending always loops back at its own end, by definition, whether or not `:|` was separately toggled — without it, `ending: 1`/`ending: 2` with no explicit `:|` played both endings back to back with no repeat at all, an easy trap since marking "1." reads as sufficient on its own. `nextRepeatEnd` (the second-pass skip-target lookup) calls `endsRepeat` too, so the implicit and explicit cases are found identically. `LeadSheet.jsx` calls `endsRepeat` as well (precomputed once per render as `impliedRepeatEndIds`, scanned over the real `progression` so a wrapped-row ending is still found) so the printed repeat barline always matches what plays — the ending brackets themselves don't need this, since they're drawn from `ending` alone, independent of any repeat-end.

Sections are created two ways: "Add section" appends one at the end, and the `§` button on each chord card (`startSectionBefore` in `App.jsx`) inserts one *before that chord* — needed because a section added after the fact would otherwise have to be walked back with the ← arrow one chord at a time. The suggested name is the first unused letter A–Z, both flows use `window.prompt` (blank/cancel is a no-op), and clicking a section's name renames it (`renameSection`). The `§` button is disabled on a chord that already directly follows a section marker.

This "marker as just another array entry" design is deliberate: reordering (`moveChord`), duplication (`duplicateChord`), and removal (`removeChord`) in `App.jsx` are all generic over `id` and don't care about `type`, so sections move/duplicate/delete exactly like chords with no special-casing. Anything that *does* need to distinguish them (rendering, playback, export) checks `entry.type === 'section'` explicitly — see `Progression.jsx` (branches to `SectionMarker` vs `ChordCard`), `utils/audio.js`'s `playProgression` (`unfoldRepeats` returns chords only, so sections don't make sound or consume playback time), and `utils/exportProgression.js` (emits a different shape per type).

`ids` are generated with `crypto.randomUUID()`. `App.jsx` lazy-initializes progression state from `src/utils/storage.js` (`localStorage` key `pianograph:progression`) and persists on every change via `useEffect`. Storage reads/writes are wrapped in try/catch since `localStorage` is an external-boundary API that can throw (private browsing, quota); `loadProgression()` also normalizes entries loaded from before `type`/`beats` existed, so old saved data doesn't break — extend that normalization if the entry shape changes again.

`src/utils/exportProgression.js` builds `Blob` + synthetic anchor-click downloads for JSON and plain-text export — no backend involved. The JSON shape is `{ title, beatsPerMeasure, playOrder, progression: [...] }` (chord entries drop `id`), and files are named from the song title.

The song title is separate document state in `App.jsx` (`localStorage` key `pianograph:title`). It renders as a heading on the lead sheet (so it prints), and an effect also sets `document.title` because browsers use the page title as the default filename when saving a print as PDF. `clearProgression` clears the title along with the progression — treat "Clear" as starting a new song, not just emptying the current one, so anything else added as song-level state (like `beatsPerMeasure`) should be reconsidered for the same treatment if a future change makes it feel similarly "left behind."

`src/utils/importProgression.js` (`parseImportedSong`) is the trust boundary for imported JSON files: it accepts the current `{ title, beatsPerMeasure, progression }` shape and older plain-array or pre-time-signature exports (which default to 4/4; chords missing `beats` default to one full measure), validates every entry (throwing user-facing `Error` messages the UI shows verbatim), normalizes notes to sharp-spelled ids via Tonal, regenerates all ids, and **recomputes each label** from the notes with the current sharps/flats setting rather than trusting the file. Validation runs before the "replace your current progression?" confirm, so a bad file never prompts. If the entry shape changes again, update this parser, `storage.js`'s `normalizeEntry`, and the exporter together.

`src/utils/importMidi.js` (`parseImportedMidi`) is a second import path, from a `.mid` file, producing the same `{ title, beatsPerMeasure, progression }` shape so `App.jsx`'s `applyImportedSong` handles both identically. It's built for **quantized block-chord files** (a fake-book/chord-chart export), not an expressive performance — see the file's header comment. It parses with `@tonejs/midi` and works in **ticks**, not seconds, so per-note tempo variation in the file (one real-world test file had 100+ tempo changes) doesn't affect the result. `clusterByOnset` groups notes into a chord whenever their start ticks fall within 1/32 beat of each other; a chord's length is the gap to the *next* cluster's onset (not its own notes' note-off), so a slightly late release doesn't shorten the following chord — the tradeoff is that a genuine rest is invisibly absorbed into the chord before it. The time signature is converted to a whole number of quarter-note beats (so 6/8 becomes 3) and falls back to 4/4 if that isn't a supported whole number. Labels are recomputed with `chordLabel` exactly like everywhere else, even where the file carries its own chord name as a MIDI `lyrics` event — that text is never trusted, and can legitimately disagree with Pianograph's naming for an inversion or a voicing missing its fifth.

### Song form: playback-only, layered on top of sections

A song form lets you play sections in a custom order — A, B1, A, B2, A — without duplicating chords or touching `progression`/the lead sheet, which always show each section once in document order (real charts write a section once and rely on the player knowing the form). `src/utils/sections.js` has both halves: `listSections(progression)` groups the flat array into `{ id, name, chords }` per section (the same grouping the lead sheet already needed, now shared by the lead sheet, the section chips, and this), and `buildPlayOrder(progression, order)` takes an array of section ids — repeats allowed — and concatenates each one's marker-plus-chords into a flat `playProgression`-shaped array. Chord entries, including their ids, are reused as-is, so a chord played on its second pass through the form still highlights the one physical card that represents it.

`App.jsx` holds the order as `formOrder` (persisted via `storage.js`'s `loadFormOrder`/`saveFormOrder`, `localStorage` key `pianograph:playOrder`). A step whose section has been renamed away or removed is pruned **during render**, not in a `useEffect` — the same `clearSignal`-style pattern as `Piano.jsx` above, keyed on a joined string of the current section ids so unrelated `progression` changes (editing a chord's notes) don't trigger it. `components/SongForm/` renders nothing at all when fewer than two sections exist, so a pruned-down order can sit in state with no UI for it until a second section exists again.

**Export/import.** Ids are regenerated wholesale on every import and the file format never stored them (`exportProgression.js` already drops chord ids too), so `formOrder` can't be written to a file as ids. `exportProgressionAsJson` instead writes each step as its *position* among the sections in document order (`playOrder: [0, 1, 0]`, 0 = first section); `parseImportedSong` maps those positions back through a fresh `listSections` call once the new progression — and its new ids — exists. An out-of-range index is silently dropped rather than failing the whole import.

### Leadsheet view and print/PDF export

`src/utils/leadsheetLayout.js` (`buildLeadSheetRows`) turns the flat progression array into rows ("systems"): a section marker always starts a new row (and supplies that row's label), and chords also wrap to a new row once a row's total `beats` would exceed `maxBeatsPerRow`. `LeadSheet.jsx` chooses that cap per row from the measured sheet width (`ResizeObserver`): `buildLeadSheetRows` accepts a function of the row's measures, and `makeRowCapacity` requires at least 48px per beat *and* enough room per chord for its diagram at ≥80% of natural size (`MIN_DIAGRAM_SCALE`) — so a row of short chords with wide diagrams holds fewer chords while ordinary 4-beat rows are unaffected. Capacity is always a whole number of measures, at most four (`MAX_MEASURES_PER_ROW`), so an iPad gets shorter rows than a desktop. Mini-diagram white keys use the softer `--key-outline-soft` outline so highlighted keys stand out at small sizes; add that token to the paper scope and print block alongside the other `--key-*` ones. This is the one place that interprets the two entry types into a layout structure — keep it a pure function of its inputs.

`src/components/LeadSheet/LeadSheet.jsx` renders each row as a hand-drawn SVG staff (5 lines + barlines, no music-engraving library — there's no melody data in this app, only chords, so real notation engraving isn't needed) plus a treble clef drawn as an inline SVG path (`trebleClef.js`, outlined from the OFL-licensed Bravura font — a Unicode `𝄞` character rendered at a different size and font on different devices and in the exported PNG, and sat off the staff). The key layout trick: each measure's chord-name/`PianoDiagram` annotation cell uses `flex: <beats> <beats> <beats * 30px>` (grow, shrink, *and* basis all scaled by `beats`), so its rendered width stays proportional to `beats` whether the row is compressed or stretched — and the SVG staff below it uses `viewBox="0 0 totalBeats 8"` with `preserveAspectRatio="none"`, so its barlines land at the same proportional x-positions. Both layers independently resolve to the same per-chord width from the same `beats` ratios, which is what keeps chord annotations aligned with the staff without any manual pixel syncing. If you change one sizing scheme, change the other to match. Barlines are drawn at *measure* boundaries (every `beatsPerMeasure` beats from the row start), not between chords; a chord that straddles a measure boundary simply has a barline pass through its cell. Because a cell can now be narrow (two chords per measure), `PianoDiagram` is fluid — it has a natural width but `max-width: 100%`, with percentage-based key and black-key positions — and the sheet shows only the *primary* chord name (`label.split(' / ')[0]`) rather than every alternate reading.

**Handwritten chord names** is a toggle, not a fixed choice: a checkbox (`handwritten` state in `LeadSheet.jsx`) puts a `.handwritten` class on `.leadsheet-paper`, and `LeadSheet.css` uses that to swap `.leadsheet-chord-name`'s font to Architects Daughter (SIL OFL, bundled in `public/fonts/`) at a larger size — script fonts have no bold face, so `font-weight` is reset to normal rather than left to inherit a synthesized (poor-looking) bold. Persisted via `storage.js`'s standalone `loadHandwrittenChords`/`saveHandwrittenChords`, a dedicated key rather than folded into `loadPreferences`, since nothing outside `LeadSheet` needs it. Two things this depends on: `useSheetImage`'s `version` memo must include `handwritten` (otherwise toggling it wouldn't invalidate the cached PNG), and `renderSheetPng` awaits `document.fonts.ready` before capturing (the font loads lazily on first use since the toggle defaults off, and html-to-image would otherwise rasterize the fallback font if capture raced ahead of that load).

Repeat marks render in `StaffRow`: each measure carries its flags from `buildLeadSheetRows`, and `LeadSheet.jsx` draws repeat glyphs as absolutely positioned **HTML** elements (`.repeat-mark`) at `left: beat / totalBeats * 100%` rather than SVG shapes, because the staff SVG is stretched non-uniformly (`preserveAspectRatio="none"`) and would squash the dots. A glyph replaces the plain barline at the same position. Endings render as brackets (`.leadsheet-ending`) in a strip above the chord annotations, one per run of contiguous chords sharing an ending; a bracket that wraps onto the next row is re-drawn and re-labelled there. All of these use the same beat-fraction positioning as the chord cells, so alignment carries over. Staff lines and barlines use `vector-effect="non-scaling-stroke"` so they stay 1–1.5px regardless of the stretch (which also keeps a repeat's thick bar visibly heavier than a plain barline).

**Sharing.** The lead sheet toolbar has **Share** (native share sheet, shown only when `navigator.canShare` accepts files) and **Download PNG**, both in `utils/sheetImage.js`. `useSheetImage` in `LeadSheet.jsx` renders the paper to a PNG with `html-to-image` in the background (400ms debounce, re-run whenever the rows, title, or width change) and keeps the blob ready, so Share can be called synchronously from the tap — iOS Safari only allows `navigator.share()` during a user gesture, and rendering after the tap can lose that activation. "Preparing" is derived from a `version` object rather than set in an effect. The capture target is `.leadsheet-paper`, an inner element with no border/shadow (the card border lives on the outer `.leadsheet-sheet`), and `renderSheetPng` renders twice and keeps the second because html-to-image can return a blank first pass in Safari (this is untested on real Safari). **Gotcha:** html-to-image inlines computed styles onto HTML elements but *not* onto shapes inside an SVG, and the standalone image has no stylesheet, so any SVG element styled only by a CSS class renders invisible in the PNG — give SVG shapes their `stroke`/`fill`/`vectorEffect` as attributes, as the staff lines, barlines, and clef do.

`App.jsx` holds a `view` state (`'builder' | 'leadsheet'`) that swaps which panel renders — not two panels shown at once. Print support piggybacks on this: a global `.no-print` utility class (in `index.css`, under `@media print`) hides chrome (the view-toggle button, the leadsheet's own "Print / Save as PDF" button) when printing, and `#root`'s padding/min-height are relaxed under `@media print`, which also sets `print-color-adjust: exact` on the sheet (browsers otherwise drop background colors unless the user ticks "Background graphics", erasing the black/highlighted keys) so the leadsheet uses the full page. The print button just calls `window.print()` — no PDF-generation library; this relies on the browser's own print-to-PDF (works from Chrome/Edge's print dialog and from iPad Safari's print preview share sheet).

### Help and first-run hints

Instructions live in two places: `components/HelpDialog/HelpDialog.jsx`, a `?` button in the header that opens a native `<dialog>` (`showModal()` gives Escape-to-close, focus handling, and a backdrop for free; a click on the dialog element itself, not its content, closes it), and the empty state in `Progression.jsx` (three short steps that disappear once a chord exists). ### Styling: tokens, shared controls, and the "paper" scope

All colors, radii, and shadows are CSS custom properties defined once in `src/index.css`, with a `prefers-color-scheme: dark` override block (dark mode follows the OS; there's no manual toggle). Component CSS should use those tokens (`var(--surface)`, `var(--accent)`, `var(--key-white)`, …) rather than hardcoded colors — the piano and mini-diagram keys have their own `--key-*` tokens so they stay correct in dark mode. Shared controls live in `index.css` too: `.btn` (+ `-primary`/`-secondary`/`-ghost`), `.icon-btn`, `.input`, `.panel`. Both button types grow under `@media (pointer: coarse)` for touch (the card icon buttons are 40px there, sized to fit five across a card; `.btn` is 44px).

The lead sheet is deliberately **always light "paper"**: `.leadsheet-sheet` in `LeadSheet.css` re-declares the text and `--key-*` tokens locally with fixed light values, so it stays white with dark ink in dark mode. Print does the same globally — the `@media print` block in `index.css` re-declares the light tokens, so printing from dark mode still produces dark-on-white output. If you add a new token that the lead sheet or piano diagrams use, add it to the paper scope and the print block too.
